## 一、架构解耦（需求 1：系统/监控/登录与 stock 隔离）

### 现状（已探查结论）
- `system/` 包 → 业务包：**零依赖**（system 从不 import 任何业务类）。
- 业务包 → `system/` 包：**零依赖**（仅用 `@SaCheckPermission` 注解，不直接引用 SysUser 等实体）。
- `auth/` → `system/`：AuthService 依赖 SysUser/SysUserMapper/MenuService（需接口化）。
- `dataperm/` → 双向依赖：**最强耦合点**，同时 import 业务实体(strategy/factor/backtest) 和 system 实体(SysUser)。
- DB 层：**业务表无 sys_ 外键**，天然可拆分。
- 前端：`RequireAuth.jsx` 有硬编码 `ROUTE_PERMISSIONS` 路由权限映射。

### Phase 1：包级隔离（不改功能，只挪位置）— 工作量 L，优先级 P1

| 子项 | 动作 | 涉及路径 |
|---|------|---------|
| X1-a | 新建 `platform-core` Maven 模块 | 项目根新增 `platform-core/` |
| X1-b | 搬迁后端包：`auth/`、`system/`、`credential/`、`audit/` | `backend/.../auth`、`system`、`credential`、`audit` |
| X1-c | 搬迁公共子包：`common/config/`、`common/ratelimit/`、`common/security/`、`common/utils/` | `backend/.../common/{config,ratelimit,security,utils}` |
| X1-d | `backend/pom.xml` 加 `<dependency>platform-core</dependency>`，删除已搬源码目录 | `backend/pom.xml` |
| X2 | **dataperm 重构**：`ResourceType` 枚举移到 platform-core；`DataPermissionService` 不再 import 业务 Mapper，改为**业务模块 SPI 注册"受控资源表名"**；`sys_department` 表名改为可配置 | `dataperm/` 全部 |
| X3-a | 前端 `pages/system/` 抽为独立 lazy-load bundle | `frontend/src/pages/system/` |
| X3-b | `RequireAuth.jsx` 的 `ROUTE_PERMISSIONS` 硬编码 → 改为从 `/auth/me` 返回的 permissions **动态校验** | `frontend/src/RequireAuth.jsx`、`api/auth.js` |
| X3-c | API 层 `api/system.js` + `api/auth.js` 归属 platform 前端包 | `frontend/src/api/` |

### Phase 2：DB 物理分离（可选，远期）— 工作量 L，优先级 远期

| 子项 | 动作 |
|---|------|
| X4-a | `sys_*` + `resource_meta`/`resource_share` + `notification_config`/`sla_config`/`task_run_history` → 归 `platform_db` |
| X4-b | `stock_*`/`factor_*`/`backtest_*`/`strategy*` 等 → 归 `stock_db` |
| X4-c | 经 Spring 多数据源 或 微服务 RPC 连接 |

> **为什么现在做 Phase 1 最划算**：业务表无 sys 外键、system 不依赖业务，当前耦合度最低，基本是"搬文件夹 + 加一个 Maven 模块 + 解一个 dataperm 耦合"。越往后加的业务越多，dataperm 绑定的资源类型越多，拆分成本越高。

## 二、五大需求缺口（截图 #2/#6/#7/#8/#9）

### #6 字典管理 — 优先级 P1（最该做）
- **现状**：全仓搜 `sys_dict` → 0 匹配，字典功能完全缺失。
- **本系统作用**（4 大场景）：① 统一因子/策略/回测各自一套、命名不一致的状态枚举；② 替代选股页 6 套硬编码下拉；③ 收归 SLA 严重级/任务触发类型/通知渠道等散落枚举；④ 承载财务/交易/告警/事件类别。
- **实现**：`sys_dict_type` + `sys_dict_data`(value/label/sort/color/ext_json/enabled) + `DictController` + `DictService`(CRUD+按 type 查+缓存 evict) + 前端管理页 + `useDict(type)` hook。
- **依赖**：F1 字典框架。详见第三节与 `字典化改造清单.md`。

### #7 参数配置中心 — 优先级 P1–P2
- **现状**：参数散落各处——`application.yml`(cron 开关、scriptTimeoutMinutes)、`notification_config`(通知渠道)、`sla_config`(SLA 阈值)、Java `@Value`。改限流阈值要改 yml 重启。
- **实现**：`sys_config` 表(key-value + group) + 后端启动时加载内存缓存（参考 `NotificationConfigService` 模式）+ 支持热更新不重启 + 轻量管理页。
- **迁入项**：限流阈值 / QPS 上限 / 脚本超时 / 全局 cron 开关。不做版本/回滚/灰度。
- **依赖**：D0（归属 platform-core）。

### #8 系统监控面板 — 优先级 P2
- **现状**：任务维度(刚做的 TaskRunHistory) + 数据维度(DataQualityDashboard) 已有；缺 JVM/OS 维度。
- **实现**：引入 `spring-boot-starter-actuator`（零代码暴露 /actuator/metrics /health /info）+ 自建轻量页聚合：
  - JVM：堆使用率/GC 次数耗时/线程数（`ManagementFactory`）
  - HTTP：QPS/平均响应（Filter 统计）
  - CH：最近 N 次 ClickHouse 查询耗时（JdbcTemplate 包装器）
  - 任务：复用 `task_run_history` 聚合
- **依赖**：D0（归属 platform-core）。不上 Prometheus+Grafana（单机太重）。

### #2 在线用户管理 — 优先级 P2
- **现状**：Sa-Token 内置 `kickout`/`token-timeout`，但无管理界面查看在线列表+强制下线。当前仅少数内部用户，价值低。
- **实现**：后端用 `StpUtil.searchSessionId(...)` + `getSessionByLoginId(...)` 实现在线列表；1 个 Controller + 1 个前端页。
- **依赖**：D0（归属 platform-core）。未来开放多人使用时升 P1。

### #9 用户行为统计 — 优先级 P3（远期）
- **现状**：单人/少人内部工具阶段，日活=登录次数，无统计意义。
- **实现**：需埋点基建（前端 route 切换事件 + 后端接口访问日志聚合）。
- **依赖**：R8（监控面板先做，复用其指标采集）。

## 三、字典化改造（33 类型）— 与第一节地基的关系

> 完整 33 类型 / 40+ 常量点 + 行号见 `字典化改造清单.md`。此处给分组摘要与"为什么必须先在 platform-core 里建框架"。

### 改造分类
- **A 类（纯前端）**：标签/颜色/下拉改为 `useDict(type)`，无后端逻辑（30 类）。
- **B 类（含后端逻辑）**：后端有 `CASE WHEN`/过滤依赖枚举值，须同步改（3 类：`SLA_SEVERITY`/`MENU_TYPE`/`NOTIFY_CHANNEL`）。

### 分组与优先级
| 批 | 字典类型 | 个数 | 典型位置 |
|---|---------|------|---------|
| K-P1 | `SLA_SEVERITY`(B)、`TASK_STATUS`、`TASK_TRIGGER_TYPE`(B)、`FACTOR_STATUS`、`STRATEGY_STATUS`、`BACKTEST_STATUS`、`NOTIFY_CHANNEL`(B)、`MENU_TYPE`(B) | 8 | 多页不一致状态 + 唯一后端 `CASE WHEN`（`TaskRunHistoryController.java:92`） |
| K-P2 | 选股 6 套(`SCREEN_*`)、滚动 4 套(`ROLLING_*`)、`REPORT_TYPE`、`RESEARCH_RATING`、`SELL_ACTION`、LLM 2 套(`LLM_RISK_LEVEL`/`LLM_REC`)、`MARKET`、`DATA_QUALITY_LEVEL`、`SECTOR_CATEGORY` | 18 | `StockScreen.js`、`RollingBacktestReport.js`、`FinancialData.js`、`LlmAnalysisPage.js` 等 |
| K-P3 | `RECOMMEND_CORR_GROUP`、`RECOMMEND_REASON`、`ALERT_TYPE`、`EVENT_TYPE` | 4 | `RecommendationList.jsx`、`PaperTradingPage.js` |

### 与需求的关系
- **R6（字典管理功能）** = 建框架 + 第一个吃螃蟹的运维界面。
- **K-P1/P2/P3** = 把存量硬编码项迁到框架上。R6 完成且 F1 就位后，K 系列才能逐批做。
- **关键铁律**：业务代码改"遍历字典列表 + 读属性(sort/color/ext_json)"，禁止 `switch(value){case A...}` 枚举全部可能；未知值默认兜底（排最后/默认色），保证新增枚举透明不崩。

## 四、依赖关系与推荐实施顺序（关键路径）

```
D0 platform-core 骨架
  └─ F1 字典框架
       ├─ R6 字典管理功能
       │    └─ K-P1 字典化(含 SLA_SEVERITY 后端改造)
       │         └─ K-P2 → K-P3
  └─ R7 参数配置中心
  └─ R8 系统监控面板
       └─ R9 用户行为统计
  └─ X1 解耦 Phase1(搬包)
       └─ X2 dataperm→SPI
       └─ X3 前端去硬编码
            └─ X4 解耦 Phase2(分库) [远期]

推荐批次：
【第 0 批·地基】D0 → F1
【第 1 批·解耦+字典】X1 → X2 → X3 → R6 → K-P1
【第 2 批·运维面板】R7 → R8 → R2
【第 3 批·字典铺开】K-P2 → K-P3
【第 4 批·远期】R9 → X4
```

### 为什么这个顺序
1. **D0/F1 必须最先**：R6 与全部 K 系列都依赖字典框架；不先搭好 platform-core，字典代码无处安放。
2. **解耦 X1 紧随**：趁耦合度最低时搬包，且把 dict/config/monitor 直接落进 platform-core，避免二次迁移。
3. **R6 在 K-P1 前**：先有"字典管理"运维界面，才能在前端给 SLA 加 CRITICAL 并立刻在 K-P1 的看板看到效果，形成闭环验证。
4. **R7/R8 独立**：不依赖字典，可与字典并行，但需 platform-core 容器就位。
5. **X4 最后**：物理分库只有在所有功能都进了 platform-core 后才有意义，否则要反复挪数据源。
